# Apple sources

Reviewed on 10 October 2026. Headroom is independently implemented with Apple frameworks, its own generated HDR sample, documentation, and local experiments. Reference-app behavior was inspected during research; no Lunar code or assets are included. Release 0.4.0 uses no private macOS APIs. The local 0.5.0 candidate isolates one private integration in a compatibility adapter: reading and setting native hardware brightness. Its Display + overlay uses public AppKit and SwiftUI controls.

## Display behavior

- [AVPlayerLayer.isReadyForDisplay](https://developer.apple.com/documentation/avfoundation/avplayerlayer/isreadyfordisplay) indicates first-frame readiness; [current EDR headroom](https://developer.apple.com/documentation/appkit/nsscreen/maximumextendeddynamicrangecolorcomponentvalue) separately indicates the available display range. Build 13 waits for both conditions instead of adding a fixed startup delay. Neither condition measures physical luminance.
- [Determining support for EDR values](https://developer.apple.com/documentation/metal/determining-support-for-edr-values): potential headroom above 1 indicates EDR support; current headroom must be checked separately. Capability does not mean extra range is presently available.
- [Performing your own tone mapping](https://developer.apple.com/documentation/metal/performing-your-own-tone-mapping): SDR white corresponds to a component value of 1, and EDR rendering must account for current headroom. This does not promise brighter content in other applications.
- [CAMetalLayer.wantsExtendedDynamicRangeContent](https://developer.apple.com/documentation/quartzcore/cametallayer/wantsextendeddynamicrangecontent): used by the earlier Metal experiment. The menu app uses the paused HDR carrier described in [the method](docs/METHOD.md).
- [Reference EDR headroom](https://developer.apple.com/documentation/appkit/nsscreen/maximumreferenceextendeddynamicrangecolorcomponentvalue): reference rendering capability is distinct from current and potential headroom.
- [CGSetDisplayTransferByTable](https://developer.apple.com/documentation/coregraphics/cgsetdisplaytransferbytable(_:_:_:_:_:)): specifies RGB gamma tables, with documented samples in the 0–1 range. Headroom's scaled values above 1 are outside that range even though the function itself is public.
- [Quartz Display Services](https://developer.apple.com/documentation/coregraphics/quartz-display-services): provides table capacity, original samples, and actual returned sample count. Headroom captures these before changing the display.
- [CGDisplayRestoreColorSyncSettings](https://developer.apple.com/documentation/coregraphics/cgdisplayrestorecolorsyncsettings()): restores ColorSync defaults for all displays. Headroom's normal recovery instead restores the captured tables for the affected display.

Apple DTS [reproduced successful transfer-table writes and matching readback without a visible change](https://developer.apple.com/forums/thread/819331) on an M5 Max running macOS 26.3.1, including built-in and external displays. The latest Apple response visible at review still described the reported bugs as open and under investigation. This establishes why readback alone is insufficient; it does not prove that every later OS release or every Mac has the same behavior. Other participants' reports about automatic brightness and HDR interactions are compatibility test leads, not verified Headroom results.

## Brightness keys — next beta

- Lunar's pinned [MediaKeyTap implementation](https://github.com/alin23/MediaKeyTap/blob/5b8ee686bc90d917cba4f029b47c2a8541a4f58d/MediaKeyTap/MediaKeyTapInternals.swift#L248-L255) uses an active session tap. Its [brightness key mappings](https://github.com/alin23/MediaKeyTap/blob/5b8ee686bc90d917cba4f029b47c2a8541a4f58d/MediaKeyTap/MediaKeyTap.swift#L122-L129) include alternate keycodes 144/145 as well as system-defined events. Headroom independently handles those two formats, including paired releases; it does not remap F14/F15.
- [CGEvent.tapCreate](https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate(tap:place:options:eventsofinterest:callback:userinfo:)): installs the event tap used to handle brightness media keys. Other events pass through.
- [CGGetEventTapList](https://developer.apple.com/documentation/coregraphics/cggeteventtaplist(_:_:_:)): reports tap ownership, enabled state, options and event mask. It verifies the running GUI's active session tap. The current mask includes system-defined events plus key-down/key-up for alternate brightness keycodes; ordinary keys pass through unchanged and their text is never read or retained.
- [AXIsProcessTrustedWithOptions](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions) and [Apple's Accessibility permission instructions](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac): Headroom starts keyboard monitoring with the app and requests permission when needed. The user must grant it before interception can operate; the menu reports missing permission. This does not require Screen Recording.
- [Advances in macOS Security](https://developer.apple.com/videos/play/wwdc2019/701/): distinguishes passive event listening, which requires Input Monitoring, from an active filter, which requires Accessibility. Headroom uses an active filter so it can consume supported brightness events across hardware, boost, and extra dimming ranges.

`NormalBrightnessReader` dynamically resolves `DisplayServicesGetBrightness` and `DisplayServicesSetBrightness`. These functions are private and have no public Apple API contract. Their C signatures were checked against Lunar's published [v6.9.5 declarations](https://github.com/alin23/Lunar/blob/v6.9.5/Lunar/DDC/Lunar-Bridging-Header.h#L45-L46) and [native-control call sites](https://github.com/alin23/Lunar/blob/v6.9.5/Lunar/Control/AppleNativeControl.swift#L82-L105): the getter takes a display ID and `float *`, the setter takes a display ID and `float`, and both return an integer status. Headroom independently loads the symbols at runtime, rejects invalid levels, checks the return status, and waits for readback before crossing ranges. An unavailable adapter or failed native operation leaves ordinary keys to macOS. Headroom does not change the automatic-brightness preference.

For supported displays, Headroom owns the normal keyboard range as well as both extra ranges. Holding Down reduces native brightness to 0.01 before entering software dimming; holding Up reaches native maximum before entering boost. The 0.01 hardware floor is a slider setting, not a physical luminance percentage. Up from hardware zero raises native brightness; Down leaves zero unchanged. The existing transfer-table and recovery path supplies both extra ranges. Extra dimming scales the saved baseline downward to a minimum factor of 0.1 and does not activate the HDR carrier. This factor is not a measured luminance ratio. Quit restores temporary color-table changes while preserving the user's selected hardware-brightness level.

Headroom's single Display + overlay covers supported adjustments across all three ranges. It uses [NSGlassEffectView](https://developer.apple.com/documentation/appkit/nsglasseffectview) and a native SwiftUI [Slider](https://developer.apple.com/documentation/swiftui/slider) on macOS 26 or later, with [NSVisualEffectView](https://developer.apple.com/documentation/appkit/nsvisualeffectview) for older systems. It is Headroom's own panel built with Apple controls, not Apple's system banner. The bar represents a control position, not measured luminance.

On the test Mac, Control Center explicitly ignored legacy OSD requests; reaching its service did not establish a visible indicator. The direct modern banner interface required Apple's private system-banner client entitlement and refused Headroom's probe. Headroom does not change that restriction or use either route. See [validation](VALIDATION.md) for the probe evidence and current overlay checks.

Accessibility approval and an enabled brightness-only session tap were verified for an earlier candidate GUI. A separate shell-launched diagnostic was attributed to Codex and reported its own untrusted context; it did not describe the GUI's permission state. Build-specific results and remaining live checks are recorded in [VALIDATION.md](VALIDATION.md).

## Lifecycle and distribution

- [Display reconfiguration callbacks](https://developer.apple.com/documentation/coregraphics/cgdisplayreconfigurationcallback): display changes require reconciliation; an old numeric display ID is not sufficient for recovery.
- [NSWorkspace sleep notifications](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification), [wake notifications](https://developer.apple.com/documentation/appkit/nsworkspace/didwakenotification), and [display sleep notifications](https://developer.apple.com/documentation/appkit/nsworkspace/screensdidsleepnotification): system and display sleep are separate lifecycle events.
- [Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution): describes the Developer ID signing and notarization workflow for software distributed with Apple's checks. Headroom 0.4.0 instead provides source and an ad-hoc beta: that signature supplies neither a Developer ID identity nor an Apple notarization ticket, and downloaded copies may be blocked by macOS.
- [TN3127: Inside Code Signing: Requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements): explains how a designated requirement identifies code across versions. An ad-hoc signature is tied to a particular build, so an updated beta may need Accessibility approval again. Headroom does not weaken this identity check or modify permission records.

The installed SDK headers were also checked for table range/sample count, EDR properties, and all-display ColorSync restoration behavior. These references describe API contracts. Actual test results and remaining checks are in [VALIDATION.md](VALIDATION.md).
