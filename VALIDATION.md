# Validation

Recorded on 10 October 2026. This record separates the current menu app from the earlier Metal lab and separates API results from physical measurements. The repository contains a [sanitized results summary](docs/validation-results.json); raw local logs, device identifiers, and recovery tables are excluded.

## Completed checks

### 0.5.0 brightness-key candidate

Build 13 addresses cold boost startup latency after the reported Up-on-release behaviour. The earlier integration helper waited for each action to drain and checked boost activation after releasing Up; it therefore did not establish response during a hold. The revised test feeds Up repeats every 33 ms independently of queue progress and samples real native brightness and gamma every 50 ms before sending key-up.

The baseline build first changed the gamma table **1,602 ms** after starting a cold boost. Build 13 removes the arbitrary 1.5-second settling period and waits for both a displayable HDR frame and current EDR headroom instead. Its first cold gamma change was **102 ms**. A separate **750 ms hold** changed gamma at **101 ms**, before release at 759 ms. Native-range response was approximately 51 ms both before and after, as was response within an already-active boost. These are sampled API readback latencies, not instrumented light measurements. The long baseline holds also changed before release, so this result isolates the startup pause rather than establishing a general key-up dependency.

All **584 replayed events** were consumed, all prior controller/failure cases passed, and the independent watchdog verified exact native/gamma restoration with no journal remaining. All 74 automated tests, the release build, and deep/strict signature verification passed. Physical event delivery still cannot be generated by the available automation. The normal-brightness and Down controller code is unchanged in this build. Build 13 is installed and running from Applications; its active key tap is enabled after refreshing the existing Accessibility grant. The previously selected boost was re-enabled and the menu reported Boosting.

Build 12 replaces the native-range handoff with one controller that owns supported brightness gestures across hardware brightness, extra dimming, and boost. Native Down stops at a slider setting of 0.01 before dimming; hardware writes are read back before range transitions. Both system-defined brightness events and alternate keycodes 144/145 are supported. Real configuration changes cancel gestures; unchanged screen notifications do not. Cleared snapshots and unavailable native control cannot pass keys through while the target's gamma restoration is pending.

**74 automated tests passed**, including 1,800 simulated full-range stress events and rejection of all other 65,534 16-bit keycodes. A separate, reproducible [integration harness](Tests/Integration/README.md) replayed **254 normalized events into the production controller**, using the real hardware setter, display tables, guardian, and HUD. It traversed native → dim → native → boost → native, checked a rapid repeat burst and release, 100 alternating presses, cancellation and late repeats, a rejected native write, a missing snapshot during restoration, and menu-owned dimming before native fallback. Every replayed managed event was consumed. Dimming at native 0.01 and table factor 0.5 matched the saved baseline scaling; transitions restored the original tables before native adjustment resumed. The production HUD window was observed visible. The trial observed no screen-parameter notifications, so it does not establish live configuration-change behavior.

The trial and an independent watchdog both verified restoration: **zero native-level difference, zero gamma sample difference, and no remaining journals**. The final native starting level was 1.0; earlier trial runs restored their starting level of 0.6875 exactly. The release build and deep/strict ad-hoc signature checks passed. Build 12 is installed and running from Applications, with its active session event tap confirmed enabled for mask 19456 after refreshing Headroom's existing Accessibility entry. Tests do not synthesize operating-system keyboard input: actual physical-key delivery and absence of a simultaneous Apple OSD remain unverified by this automation.

Build 11 was superseded after physical use exposed continued Down and duplicate-indicator failures. Its earlier policy tests did not verify the complete controller or hardware integration.

Build 11 attempted to correct a reported held-key failure. The prior policy deliberately required releasing at the native endpoints, which blocked continuous movement. Held native repeats now enter boost or dimming after a verified boundary reading, continue adjusting, and wait for restoration before returning to macOS. Release ownership is tracked separately: when macOS received the initial key-down it also receives the eventual key-up, even if Headroom captured the repeats. The normal dimming readback check now polls every 35 ms for at most 350 ms, rather than waiting for the ordinary 250 ms monitor after the first read. No synthetic key repeat timer was added. **84 tests passed** (46 key tests and 38 core/recovery tests), including held traversal from boost through normal into dimming and the reverse, release delivery, late repeats, and readback deferral. The release build and deep/strict signature verification passed. Build 11 is installed, with the running GUI's brightness-only event tap confirmed enabled after refreshing its existing permission entry. These are automated sequence and runtime checks; physical media-key delivery is not recorded as an end-to-end live pass.

The build 10 candidate passed **79 automated tests** (38 core/recovery and 41 key-policy/sequence cases), its release build, and deep/strict signature verification. It adds gamma dimming down to a factor of 0.1 and automatic brightness-key handling, with no opt-in menu item. Dimming uses the original saved tables and creates no HDR carrier. A bounded live run at factors 0.95, 0.75 and 0.9 matched baseline scaling exactly. ## What the numbers mean

The current EDR value is a rendering allowance reported by macOS. A transfer-table readback reports the API's stored state. Neither proves physical luminance gain. Apple DTS has reproduced successful writes and matching readback with no visible effect on another Mac/OS combination; see [Apple sources](APPLE-SOURCES.md).

During the menu scale sweep, table readback capped values at 1.0. At factor 1.75, 439 of 1,024 samples per channel formed the upper plateau; at factor 2.0, 512 did. This establishes the API's clamping behavior. It does not resolve final compositor highlight clipping or color accuracy. The slider must not be described as “twice as bright.”

No brightness in nits, contrast ratio, color error, battery-life change, or sustained total GPU power has been measured. A ten-second **lab-only** sample used approximately 0.276% of one CPU core for the lab and 0.103% for the helper, with approximately 73.9 MB and 12.7 MB resident memory. It excluded WindowServer and display power and is not a performance claim for the menu release.

## Reproducing a useful comparison

Keep the room, display preset, system brightness, content, and window sizes fixed. Compare off/on/off using the same ordinary white document, near-white steps, neutral gray ramp, and color patches. Record the requested scale separately from perceived brightness. Verify restored transfer tables after switching off, and record any visible mismatch separately.

For each new hardware/OS combination, verify normal restoration before crash scenarios. Fault-injection tools are development utilities and should be run deliberately, with no other display-adjustment session active. A complete performance test must include compositor work and display power, not only the Headroom process.

Community beta status is appropriate while this matrix remains incomplete. Notarization will establish Apple's distribution checks; it will not certify display compatibility or validate unmeasured brightness claims.
